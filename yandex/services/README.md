# Сервисы публичного провайдера

Рукописный и сгенерированный код сервиса лежит вместе: `pluginsdk/` и `framework/` разделяют реализации по библиотеке HashiCorp. Hooks находятся рядом с обслуживаемым ресурсом; acceptance-тесты и sweepers — внутри того же сервиса.

## Добавление сервиса

1. Возьмите путь исходного RPC proto относительно `yandex/cloud/` и уберите файл и каталог версии. Например, `yandex/cloud/serverless/functions/v1/function_service.proto` соответствует `yandex/services/serverless/functions/`.
2. Подготовьте эту сервисную папку в обычном PR. Генератор проверяет её наличие и создаёт ресурсные пакеты только внутри неё. `validate-model` укажет ожидаемый путь при несовпадении.
3. Настройте генерацию в сервисном `terraform.yaml`. Один конфиг может описывать несколько API-сервисов: каталог каждого результата определяется его исходным RPC. Версии одного API используют одну сервисную папку; переименование Terraform-ресурса путь не меняет.
4. Ручную реализацию разместите по тому же правилу и подключите в сборке соответствующей реализации провайдера. Если RPC нет, согласуйте имя папки в PR. Новый сгенерированный ресурс подключается автоматически.
5. Для самостоятельного ревью команды добавьте правило в общий `a.yaml` в корне провайдера. Укажите команду и пути к коду сервиса, документации и примерам. Пока сервисного правила нет, действует общее правило ревью провайдера.

При сборке Plugin SDK проверяются имена и значения регистраций. Ошибка содержит имя сервиса и выводится при запуске провайдера. Framework проверяет регистрации при получении схемы.
